企业开始做 AI 时，需求往往看起来很直接：做一个 Agent，让它自动判断缺什么料、找供应商、给出采购建议，甚至直接创建采购任务。

站在 Agent 层看，这个需求似乎已经足够明确。模型需要读取项目需求、库存、供应商信息和历史采购记录，再按照一定规则做判断，最后调用系统完成动作。

但真正开始往下做，很快就会发现，问题会不断向前追。

什么叫“缺料”？是项目需求减当前库存，还是还要考虑已经锁定给其他项目的库存？同一种物料存在替代料时，什么时候允许替代？一个项目急需的物料和安全库存补货同时出现时，优先级怎么判断？采购需求是谁确认的，谁有权改变？供应商交期发生变化以后，谁负责重新评估项目风险？

继续追下去，还会发现系统里可能根本没有一个稳定的“采购需求”对象。项目需求、库存缺口、安全库存和人工追加采购混在一张表里；不同人通过不同流程修改数据；很多真正决定采购动作的规则只存在于业务人员脑中。

到最后，最初看起来像“做一个采购 Agent”的问题，已经不再只是 Agent 问题。

它暴露出的是一条更深的依赖链：

**业务 → 组织 → 系统 → Agent。**

这四层并不是四类可以自由拼装的能力。前一层没有解决的问题，不会因为进入下一层而自动消失，只会换一种形式继续存在。

## 01｜Agent 暴露出来的问题，很多并不发生在 Agent 层

如果只是做一个一次性的采购分析，Agent 完全可以读取几份 Excel、几段说明，再给出一个看起来合理的结果。模型很擅长处理这种任务：材料已经准备好，问题范围有限，结果最终还有人检查。

但一旦希望这个 Agent 真正进入日常业务，它面对的就不再是一组静态材料，而是一个持续变化的环境。

今天库存减少了，明天客户变更了配置，后天供应商修改了交期。一个采购动作又会反过来改变库存、项目状态和资金占用。Agent 不只需要“会分析”，还要持续知道当前现实到底是什么。

这时，很多原本可以由人凭经验补齐的模糊问题会立刻暴露。

例如，企业内部可能一直都在说“缺料就采购”，但只有真正准备自动化这个判断时，才会发现“缺料”并没有一个稳定定义。业务人员之所以过去能够工作，是因为他们会综合项目进度、库存占用、替代料、交期和经验临时判断。

当这些判断准备交给 Agent 时，问题第一次被迫说清楚：

**这个业务到底是怎么运转的？**

所以很多企业 AI 项目做着做着会开始碰到数据、流程、权限甚至组织问题，并不是项目“跑偏”了，而是 Agent 开始触碰此前被人吸收掉的模糊性。

> **Agent 暴露出来的问题，很多并不发生在 Agent 层，而是来自更早的业务、组织和系统定义。** 这些问题也不能简单用“企业数据质量不好”来概括。

## 02｜四层不是四个模块，而是一条依赖关系

最底层首先是业务。

业务层回答的不是“系统有哪些功能”，而是这个业务世界里到底有什么、它们之间如何发生关系。

还是采购的例子。在真正讨论 Agent 之前，至少要先知道什么是项目需求，什么是库存，什么是净需求，什么情况下形成采购任务；标准物料和替代料之间是什么关系；一个需求经过哪些状态；采购完成的判断标准又是什么。

这些定义形成了业务本身的基本结构。

在这之后，才轮到组织回答另一个问题：**谁对其中的什么负责。**

例如，谁确认技术需求，谁对采购缺口负责，谁可以批准替代料，谁负责供应商交期异常，项目经理到底只是知情，还是拥有决策权。所谓组织，不只是部门树，而是 Actor 与业务对象、任务和决策之间的责任关系。

当业务相对清楚，系统才有东西可以稳定承载；责任明确，才能继续谈 Agent 的边界。流程、权限和页面只是前面业务结构的数字化表达，而不是反过来用系统配置猜业务应该怎么运行。

Agent 位于更后面。它进入的是一个已经存在的业务环境，在其中感知变化、读取状态、形成判断并采取行动。

所以：

> **业务定义世界，组织定义责任，系统承载世界，Agent 在其中行动。**

这四层之间存在的是依赖关系，而不仅仅是简单分层。

## 03｜层间 Gap，是企业运行中的熵源

很多企业今天真正的问题，并不是任何一层完全不存在，而是上下层之间没有对齐。

**业务和组织之间存在 Gap 时**，最典型的现象就是职责听起来清楚，落到具体事情却说不清。

比如一句“采购负责物料齐套”，看起来已经定义了责任。但继续问下去：齐套针对项目、生产任务还是某个交付节点？技术需求发生变更以后，原采购任务谁负责失效？缺料是采购责任，还是需求确认人的责任？如果有替代料，谁拥有最终判断权？

这些问题没有定义，所谓“采购负责齐套”就只能依赖经验解释。

**组织和系统之间存在 Gap 时**，模糊性会继续传递进系统。责任边界不明确，就只能靠大量审批兜底；不知道谁应该拥有修改权，就把权限开得很大，或者全部锁死；现实中存在很多例外，就在流程里不断增加分支。最后大家觉得“系统很僵硬”“审批太多”“流程不好用”，但系统只是把组织层没有解决的问题固化了下来。

再往后，**如果系统与 Agent 之间还有 Gap**，Agent 就要继续承担上一层没有消化掉的复杂度。

对象没有稳定身份，它需要从文本判断是不是同一个东西；状态没有可靠维护，它需要从聊天和文档里猜最新情况；规则没有落在系统里，它每次都要重新读取制度；多个来源互相冲突，就让模型自己判断哪个可信。

这些做法并非完全不可用，但它们把环境中的结构问题转化成了推理成本和不确定性。

> **上一层没有被消化的问题不会消失，只会以更昂贵、更不稳定的形式传递给下一层。**

这就是我所说的“层间 Gap 即熵源”。

很多所谓的 AI 落地困难，本质上只是组织过去可以依赖人脑吸收这些熵，而现在开始尝试让机器承担它们。

## 04｜从内容到行动，对环境的要求完全不同

这并不意味着企业在业务、组织和系统全部重构完成之前，都不应该使用 AI。

恰恰相反，今天大量 AI 应用已经非常有价值。让模型整理采购记录、总结会议、生成 PPT、辅助分析异常，都可以很快创造价值。

这些场景有一个共同特点：**AI 主要在生产内容。**

内容可以存在一定程度的模糊。一个会议纪要有两种写法并不严重，一份分析报告有不同措辞也很正常；即使模型漏掉了一部分信息，后面通常还有人在阅读、理解、判断，并决定是否真的采取行动。

所以在内容层，很多问题都可以靠上下文和人工兜底。

但一旦 AI 开始从“生成内容”继续向前走，要求就会发生变化。

第一步是**决策**。

模型不只是说“我认为可能缺料”，而是要明确输出：哪些物料需要采购、哪个方案优先、风险是否达到阈值。到了这里，输出已经开始直接影响后续系统行为，因此对象、指标、规则和约束必须比内容生成更清楚。

再往前一步，是**行动**。

如果 Agent 不只是给出建议，而是直接创建采购任务、修改订单、占用库存、通知供应商，它就已经不再只是生成信息，而是在改变业务世界。

这时，一个“差不多对”的答案是不够的。

它操作的是不是正确的对象？当前状态是不是真的？这个 Actor 有没有权限执行这个动作？什么规则允许它执行？动作发生以后，会影响哪些其他对象和任务？如果执行错误，是否可以追踪、撤销和恢复？

这些都不是单纯提升模型推理能力可以解决的问题。

所以，从内容到决策，再到行动，本质上也是一条对环境要求不断提高的路径：

**内容可以容忍模糊，决策需要明确边界，行动要求稳定环境。**

这也是为什么，大家会感觉，AI 看起来这么厉害，怎么感觉一落地就靠不住？怎么企业里做了半天还是对话框？区别不在于 AI 到底聪不聪明，而在于它需要解决哪一层的任务。

如果最终仍然由人补全上下文、校验结果并决定是否执行，那么 AI 仍然主要是辅助工具。可一旦 Agent 开始持续参与业务运行，并拥有越来越多判断权和行动权，它实际上就成为业务系统中的一个 Actor。

此时，它最终一定会重新撞到业务、组织和系统层。

所以真正的问题不是：

**能不能先做 Agent？**

而是：

> **这个 AI 是在生产内容、参与决策，还是已经准备直接改变业务世界？**

越靠近行动，前面的业务定义、责任边界和系统承载就越无法绕过。

## 05｜可以从局部切入，但局部也必须从业务开始

“业务 → 组织 → 系统 → Agent”并不是一个要求企业先完成几年数字化建设的瀑布模型。企业当然不需要先把所有业务重新定义一遍，再重构整个组织，再重建全部系统，最后终于开始做 AI。现实中也几乎不可能这样推进。

更合理的方法，是从一个足够小但有明确价值的业务问题开始。

例如，只解决“某一类项目的关键物料采购”。

范围一旦缩小，问题就变得可控。先理清这个局部里的需求从哪里产生，库存怎么计算，替代关系如何判断，什么条件触发采购；再确认需求确认、采购执行、替代审批分别由谁负责；然后检查现有系统里这些对象和状态是否能够被稳定承载。

做到这里以后，再决定 Agent 应该承担什么：持续检查缺口、识别异常、生成建议，还是在满足某些条件时直接创建采购任务。

整个过程可能只覆盖企业业务的一小部分，但这个小范围内部仍然跑完了：

**业务 → 组织 → 系统 → Agent。**

> **可以局部切入，但不能跳层。**

这也是为什么“从业务开始”并不等于“大而全重构”。真正重要的是，在准备自动化的那个局部里，先建立一个足够清楚的小世界。

**全局完整不是前置条件，局部闭环才是。**

与其在一个大而混乱的环境上叠一个越来越聪明的 Agent，不如先找到一个价值足够高的问题域，把这个局部理顺，再让 Agent 真正跑起来。

## 06｜AI 改变了 Actor，但没有取消业务世界

传统企业里，绝大多数工作由人和系统共同完成。Agent 的出现，本质上是在这个环境里增加了一类新的 Actor。

过去由人观察报表、判断异常、发起任务；未来其中一部分可能由 Agent 完成。过去系统主要承担存储、流程和规则执行；未来 Agent 可以在这些稳定结构之上承担更多解释、判断和行动。

变化的是 Actor 的能力和组成，而不是业务世界突然不再需要结构。

客户仍然是客户，订单仍然拥有状态，采购任务仍然需要明确责任，规则仍然决定什么可以做、什么不能做。甚至恰恰因为机器开始真正参与业务运行，过去隐藏在人脑、会议和经验里的大量结构，第一次需要被更明确地表达出来。

从这个意义上说，AI 原生企业未必是一个“结构更少”的企业。

它更可能是一个**显式结构更多、但交互和执行更灵活**的企业：业务中的对象、关系、状态、规则和责任形成共享环境，人、传统系统和 Agent 根据各自能力与权限共同参与其中。

所以，“业务 → 组织 → 系统 → Agent”并不是一套传统数字化方法披上 AI 外衣。

它表达的是一个更简单的依赖事实：

> **业务定义世界，组织定义谁对世界负责，系统让这个世界稳定运行，Agent 才能在其中可靠地理解和行动。**

AI 落地可以从任何一个局部开始。但每一个真正准备跑起来的局部，最终都需要先回答同一个问题：

> **这里的业务，到底是怎么运转的？**
