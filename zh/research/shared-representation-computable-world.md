开会的时候，只要问题稍微复杂一点，人通常都会很自然地拿起笔开始画。有人画流程，有人列时间线，有人把角色圈起来，用箭头标出关系；如果是项目讨论，可能会打开一张表，如果是架构问题，可能会直接在白板上画系统和接口。

这背后其实是一个很朴素的事实：**纯自然语言并不适合承载所有结构。**

语言擅长解释背景、表达判断和补充例外，但当一个问题里同时出现大量对象、关系、状态、约束和依赖时，听的人就不得不一边理解内容，一边在脑中还原结构，而且每个人还原出来的版本未必相同。这就是为什么方案需要“评审”，这是达成共识的必要不充分路径。

所以人类不断发明各种外部表征。流程图承载顺序和分支，表格承载对象和属性，状态机承载状态迁移，架构图承载模块与连接。它们真正的作用，是把原本隐含在脑中的结构外化出来，让多个主体能够围绕同一个对象共同观察和修改。

从这个角度看，一群人围着白板讨论，本质上是在建立共享表征。

---

今天很多 Multi-Agent 系统的协作方式，却仍然主要依赖自然语言。

一个 Agent 完成任务后输出一段文本，另一个 Agent 读进去，再生成下一段；复杂一些，就把结果写进 Markdown、Memory、Skill 或长文档，交给后续 Agent 继续处理。

这种方式当然能工作，但如果换成人来看，就很容易发现问题：一个人写三千字 Word 发给另一个人，另一个人读完后再写五千字交给第三个人，所有结构都藏在文字里，每个人都要重新解析一遍。

所以真正值得问的，也许不只是 Agent 之间应该传多少 Context，而是：**它们之间应该共享什么样的表征？**

---

这也是我提出 Cognitive IR 这个概念的原因。

IR，也就是 intermediate representation，中间表征，在编译器里早就是一个成熟概念。复杂认知任务其实也有类似需求：很多时候并不缺文本，缺的是能够显式承载结构的中间层。

它可能是一张图，用来表示对象依赖、变化传导和冲突；也可能是一张表，用来比较候选方案、约束和缺失因子；还可能是一棵树、一个状态机、一组约束、一个方程，甚至一段程序。

这些形式的价值，不是把答案写得更漂亮，而是把思考过程中真正有结构的部分保存下来，使后续主体不必每次都从自然语言中重新恢复它们。

因此，Cognitive IR 更像是一组适合人、Agent 和系统共同读写的认知结构。自然语言仍然重要，但更适合负责解释结构，而不是独自承担结构本身。

---

地图可能是日常生活里最成熟的共享表征之一。

一座城市当然也可以完全用文字描述。我们可以说：“从这里往北走三公里，经过两个路口，在第二个高架桥下面右转；继续往前，看到加油站以后左转，这条路早高峰容易堵，如果堵了可以从旁边的小路绕过去……”

纸质地图已经比这高效得多。道路、位置、方向和连接关系被压缩进一个统一坐标系里，不同的人不再需要反复通过自然语言重新描述城市，也不必各自在脑中从头恢复空间结构。

从这个意义上说，纸质地图本身就是一种很好的静态 IR。

但今天高德这样的地图显然已经不只是一张更精细的纸质地图。

道路结构仍然存在，同时还叠加了实时拥堵、封路、事故、车辆位置等持续变化的状态；这些状态不断被感知和更新，并可以进一步参与查询、路径规划和调度计算。

这里发生的变化，不只是“地图上的信息更多了”。

**静态表征开始拥有状态，能够持续映射现实，并参与计算。**

到了这一步，它已经不再只是一个供人查看的 World Representation，而更接近现实世界在数字空间中的一个运行中模型：现实发生变化，数字世界随之更新；不同主体又可以基于这份共享状态做出不同决策。

于是导航关心如何从 A 到 B，配送关心订单如何组合路线，网约车平台关心车辆和需求如何调度，应急系统关心哪些资源能够最快抵达。

这些任务并不需要统一的决策算法，它们真正需要共享的是**同一个城市，以及这个城市此刻正在发生什么。**

地图本身不是决策系统，但一张持续更新、可计算的地图，让大量不同决策能够建立在同一份现实之上。

---

企业里的 Agent 面临的是同样的问题。

采购 Agent、项目 Agent、生产 Agent、售后 Agent 可以有不同目标，也可以采用不同的智能方式。有的任务适合 LLM，有的适合规则，有的适合优化器，有的甚至只需要一个函数。

真正的问题是，如果每个 Agent 都必须从头理解一次“这个企业是什么”，它们实际上仍然生活在不同的局部世界里。

一个 Agent 里的“订单”和另一个 Agent 里的“订单”是否真的是同一个对象？项目状态改变以后，哪些任务受到影响？客户、合同、订单、项目、物料、生产任务之间的关系究竟存在哪里？现在的 ERP 更多是在说：看你们怎么定义，我们都可以通过配置支持。

这意味着，企业并不是完全没有数字化表征，而是这些表征往往被分散在不同系统、表结构、配置和文档里。系统可以承载它们，却不等于企业已经拥有了一张统一、持续更新、可计算的“业务地图”。

如果这些结构和状态只存在于各自的 Prompt、Memory、Markdown 和业务系统里，那么所谓 Multi-Agent 协作，很容易退化成多个主体反复交换自然语言，再各自补全剩下的世界。

所以，**Agent 协作真正需要的，不只是共享 Context，而是共享对现实世界的结构与状态。**

文档当然仍然是这个世界的一部分，但它应该和数据库、对象模型、关系图、状态、规则，以及 Cognitive IR 一起，共同组成表征层。

其中，Cognitive IR 解决的是很多结构如何被显式表达；而当这些结构进一步连接实例、实时状态、感知和计算时，我们得到的就不再只是一张静态的认知地图，而开始接近一个持续运行的数字世界。

这也是为什么我越来越倾向于把数字孪生理解成一种更高成熟度的表征形态：它不仅描述现实，还持续映射现实，并允许不同的决策空间建立在这份共享现实之上。

不同任务再根据自己的目标，从中抽取真正相关的局部因子，形成各自的 Decision Space。至于这个 DS 最后由 LLM、规则、函数、优化器还是人完成，并不是最重要的；重要的是，它们不需要各自重新创造一个世界。

---

人看长文会做只有自己看得懂的笔记，多人协同时，我们会寻找一个所有人都能够尽量同步理解的外部对象。

白板提供局部的共享表征，纸质地图提供静态的城市表征；而像高德这样的系统，则已经开始维护一个持续更新、可查询、可计算的数字城市。

企业里的数字世界也需要经历类似的升级：从文档和系统里分散的局部记录，到结构化的 Cognitive IR，再到能够持续承载对象、关系、状态、规则和变化的业务数字孪生。

未来的 Agent 协作，不应该主要表现为“我读完你的文档，再告诉你我的理解”，而应该越来越接近：

**多个主体共同观察、修改和操作同一个持续更新、可计算的世界。**

到了那一步，多 Agent 的协作就有了可持续维护的共同基础。
