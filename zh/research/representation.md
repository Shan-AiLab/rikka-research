AI 并不直接理解现实世界，人也一样。我们真正能够观察、讨论、计算和操作的，始终是现实经过某种转换之后形成的**表征（Representation）**。一张流程图，是对业务运行方式的表征；ERP 里的订单、客户和物料，是对现实业务对象的表征；Excel 台账、数据库表和指标看板，是对业务状态的表征；一份制度文档、PRD、Markdown 文件，同样也是表征。

地图不是城市本身，但人可以借助地图理解城市、寻找路径、判断距离。企业里的数字系统也类似：它并不是业务本身，而是现实业务在数字世界中的某种映射。我们真正能够管理和计算的，从来不是现实世界的全部，而是那个被表示出来的世界。

这件事值得被单独拿出来讨论，是因为 **AI 能理解和操作什么，不只取决于模型能力，也取决于现实被如何表征。** 模型再强，如果它面对的是一个破碎、模糊、彼此冲突的数字世界，它依然很难长期保持一致的理解，更难稳定地采取行动。

## 01｜企业数据不少，但缺足以支撑行动的表征

今天谈 Agent 时，经常会把问题归结为“企业数据不够/质量不好”。这当然是对问题的一种描述，但还不够准确。现实中的企业往往并不缺信息：数据库里有业务数据，ERP、CRM、MES 里有对象和状态，Excel 里有大量台账，“知识库”里常塞的制度、操作手册、PRD 等等各类文档，会议纪要和聊天记录里又保存着另一部分业务事实和规则。

到了 Agent 时代，这类表征还在继续增加。System Prompt、知识库、RAG 检索出来的文本、README、memory.md、handoff.md、skill.md，本质上都在承担同一个作用：告诉 Agent“这个环境是什么样的”“过去发生过什么”“接下来应该如何工作”。

所以，今天的 Agent 并不是生活在一个没有表征的世界里。恰恰相反，它周围已经堆满了表征。

真正的问题是，这些表征通常是碎片化的。同一个业务对象可能同时存在于三个系统、五张表和十几份文档里；对象的定义、当前实例和历史记录混在一起；稳定规则和临时状态没有明确区分；不同部门使用同一个词，却指向不同的东西；某项业务规则发生变化后，依赖它的流程、指标、任务和系统配置也不会自动发生关联变化。

对 Agent 来说，如果整个环境最终主要依赖文本描述，那么每一次进入任务，它都需要重新从自然语言里恢复这个世界的结构：谁是谁，什么和什么有关，哪句话是定义，哪句话描述当前状态，哪些规则仍然有效，某个变化又会影响到哪里。

于是，很多所谓的“长期记忆”，实际上更像是不断累积的工作笔记。它们当然有价值，但它们并没有自动变成一个稳定的环境模型。

这也是为什么我认为，**无限上下文不能替代稳定表征。** 上下文窗口变长，只意味着 Agent 可以一次看到更多材料，并不意味着这些材料已经形成结构一致、状态明确、能够持续更新的世界。信息可以越来越多，但世界仍然可能是散的。

所以企业 AI 落地真正需要解决的问题，不只是“AI 有没有拿到数据”，而是：**现实中的对象、关系、状态、规则、约束和变化，是否被以一种足够稳定的方式表示出来。**

## 02｜表征是对现实做有目的的投影

任何表征都是有损的。地图不会把一座城市里的每一棵树、每一块砖都画进去，企业系统也不可能把真实业务中的所有细节完整复制到数字世界中。表征真正要解决的，并不是“怎样保存现实中的一切”，而是对于当前问题，**哪些差异值得被保留下来。**

以一台大型设备为例。在销售视角下，它首先是一个报价对象，需要关注型号、配置、价格和交付周期；到了技术环节，它变成技术参数、标准产品定义和非标配置的组合；采购关心的则是进一步展开后的物料需求、库存缺口和替代关系；进入生产以后，关注点又转向齐套条件、生产任务和交付节点；设备交付之后，它又会作为一个具体实例进入售后体系，开始承载运行状态、故障和维修历史。

现实中的那个设备没有发生本体意义上的变化，**变化的是我们当前从哪里看它、为什么看它，以及需要看到多细**。因此，一个表征总是隐含着自己的坐标系：**业务域、视角、分辨率和意图**共同决定了什么被看见，什么被忽略。

这也是为什么建模并不是“越完整越好”。如果某个差异不会对当前问题产生任何后续影响，那么把它纳入当前表征，反而只是在增加复杂度。

> **一个差异是否值得被表达，不取决于它是否客观存在，而取决于它是否会在当前问题中产生后续差异。**

表征不是现实的复印件，而是一种面向认知和行动的投影。

## 03｜一个对象，通常同时需要结构化与非结构化表征

传统数字化很容易把“表征”理解成结构化数据，好像只要对象、字段和数据字典定义清楚，业务世界就已经被描述完成了。但真实业务很少这么规整。

例如，对一台设备，我们当然可以定义设备编号、型号、厂家、安装位置、当前状态、维保周期等字段。这些信息适合进入数据库，也适合形成明确的数据字典。但仅仅把这些字段定义出来，并不足以让一个新人，更不用说一个 Agent，真正理解这个对象在业务中的含义。

“状态”字段里的“停用”究竟意味着已经报废、暂时闲置，还是等待维修？为什么某一批设备的故障率明显更高？某种异常过去通常对应什么原因？某个型号为什么在特定项目里不能使用？这些内容往往存在于业务人员的经验、制度说明、维修记录、会议讨论甚至一句备注里。

这意味着，同一个业务对象通常天然同时存在**结构化表征和非结构化表征**。结构化部分适合保存身份、关系、状态和可枚举事实，非结构化部分则更适合承载解释、语境、经验和暂时无法完全形式化的知识。只保留文本，机器很难稳定计算；只保留字段，又会丢掉大量真正影响业务判断的信息。

而在两者之间，其实还存在一大片过去没有被很好承载的结构。例如依赖关系适合表示成图，分类和分解关系适合表示成树，生命周期适合表示成状态机，业务边界可能是一组约束，某些判断本身就是公式或程序。

这也是我目前把 **Cognitive IR** 单独提出来的原因。它不是试图创造一种新的万能数据格式，而是承认现实中的认知结构本来就是多种形式的：自然语言、表格、图、树、“房子图”、状态机、约束、方程和程序，各自保留现实的不同部分和它们之间的关系。

现实不会因为数据库擅长二维表，就天然长成二维表；也不会因为大模型擅长文字，就天然适合被压缩成 Markdown。

## 04｜从“记录世界”走向“运行世界”

传统数字化中的很多表征，本质上仍然偏向记录：这个客户是谁，这张订单金额是多少，这台设备发生过哪些维修，这条制度是怎样规定的。它们很好地回答了“世界被记录成什么样”，但对于 Agent 来说，仅仅能够读取事实还不够。

一个真正需要持续行动的 Actor，还需要知道现在处于什么状态，为什么形成这个状态，什么变化会影响哪些对象，哪些约束当前成立，以及执行某个动作之后可能发生什么。

这时，表征就开始从静态记录进一步变成一个可以运行的数字环境。对象不仅拥有属性，也拥有状态；关系不仅表示“有关联”，还可能承载依赖和影响；规则不仅存在于说明文档中，还能够参与判断；现实中的变化能够持续更新这个数字世界，数字世界中的判断又能够进一步驱动行动。

从这个意义上说，**数字孪生并不等于 3D 可视化。** 它更本质的含义是：现实世界中那些对当前目标重要的对象、关系和状态，可以持续映射到一个可被理解、计算和操作的数字表征中。

当表征从“给人看的记录”逐渐变成“可以被 Actor 使用的环境”，AI 才真正开始拥有一个可以长期工作的世界。

## 05｜表征是人、系统与 Agent 之间的共享接口

企业里的行动主体并不只有人。传统系统可以依据阈值和规则自动触发动作，Agent 可以观察状态、做出判断并调用工具，人则承担目标设定、复杂判断和责任。因此未来的企业环境里，人、Agent 和系统会越来越频繁地共同参与同一条业务链路。

这时，他们需要的不只是共享文档，而是对于“当前世界是什么样”的某种共享理解。

在我目前的框架中，可以把整个过程粗略表示为：

**业务世界 → 表征 → 世界模型 / Cognito Atlas → Decision Space → Action**

表征位于现实和认知之间。它决定了哪些现实能够进入数字世界，又以什么形式进入；Cognito Atlas 进一步组织这些对象、关系、流程、指标和知识；Decision Space 则针对具体目标，从已有世界中提取影响决策的因子、约束、路径和价值判断；最终，Actor 在这个基础上采取行动，并让结果重新进入表征。

如果这一层不稳定，Agent 就只能不断重新阅读世界、猜测世界，并在一次次任务中临时重建自己的理解。

而当一个足够稳定、可更新、可计算的表征层逐渐形成之后，Agent 才开始有可能不只是“读取关于这个世界的材料”，而是真正**生活在一个持续存在的数字世界里**。
